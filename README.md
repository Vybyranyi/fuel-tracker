# Пальне

Особистий облік заправок одного авто. Вносиш заправку з телефона за кілька
тапів і дивишся статистику.

Вхід — за кодом із пошти. Одна валюта, гривня.

## Що вміє

| Сторінка                 | Що там                                                                                                                                                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/` Заправка             | Форма з трьома звʼязаними полями (літри / ціна за літр / сума) — третє рахується з двох інших. Ціна підставляється з останньої заправки. Крок ±1 і ±5 літрів кнопками. Нижче — останні записи з редагуванням і видаленням. |
| `/stats` Статистика      | Картки за останній місяць зі зміною до попереднього, графіки витрат, літрів, ціни за літр і витрати на 100 км, помісячна таблиця й підсумок за весь час.                                                                   |
| `/odometer` Пробіг       | Показання одометра — одне на дату. Вносяться раз на місяць, за нагадуванням.                                                                                                                                               |
| `/settings` Налаштування | Вимикач пуш-сповіщень і перевірка звʼязку, вихід.                                                                                                                                                                          |
| `/login`                 | Вхід кодом із листа. Реєстрація відкрита: перший вхід незнайомої адреси створює акаунт.                                                                                                                                    |

## Стек

- **Next.js 16** (App Router, Turbopack) + TypeScript у strict
- **Postgres на Supabase**, **Drizzle ORM**, міграції у файлах
- **Tailwind CSS v4** + **shadcn/ui**, графіки на Recharts
- **Server Actions** через `next-safe-action`, форми на react-hook-form + zod
- **Supabase Auth** (`@supabase/ssr`) для входу, **web-push** для сповіщень
- **Vitest** для чистого домену

Потрібен Node 20.9 або новіший — цього вимагає Next 16.

## Архітектура

Залежності йдуть строго в один бік:

```
domain ← repository ← service ← action ← UI
```

`domain` — чисті обчислення: гроші, обʼєм, дати, агрегації, розрахунок
витрати. Там немає ні бази, ні React, ні Next, тому саме там і живуть тести:
кожну формулу можна запустити у вакуумі.

Код розкладено за фічами, а не за типами файлів:

```
src/
  app/                      маршрути, layout, крон-ендпоінт, іконки
  components/ui/            shadcn
  db/                       схема, клієнт Postgres, міграції
  features/
    auth/                   вхід через Supabase, поточний користувач
    fuel/                   заправки
    odometer/               пробіг
    stats/                  агрегації та графіки
    notifications/          підписки й розсилка пушів
    cron/                   щоденна задача
    pwa/                    service worker, підказка про встановлення
  lib/                      одиниці, дати, формати, спільні дрібниці
```

Напрямок залежностей — не домовленість, а правило ESLint: спроба імпортувати
базу в `domain` або репозиторій у компонент падає на лінті. Так само заборонено
тягнути `@/db` у клієнтський код.

## Локальний запуск

```bash
npm install
cp .env.example .env.local     # і заповнити
npm run db:migrate             # накотити міграції на свою базу
npm run dev
```

Якщо застосунок уже розгорнуто на Vercel, змінні швидше витягнути звідти:

```bash
vercel env pull .env.local
```

Мінімум, щоб застосунок піднявся: `DATABASE_URL`,
`NEXT_PUBLIC_SUPABASE_URL` і `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Без
ключів VAPID решта працює — сповіщення в налаштуваннях просто скажуть, що не
налаштовані.

## Змінні оточення

Повний список із поясненнями — у [`.env.example`](.env.example). Коротко:

| Змінна                                 | Навіщо                   | Звідки взяти                             |
| -------------------------------------- | ------------------------ | ---------------------------------------- |
| `DATABASE_URL`                         | Postgres для застосунку  | Supabase → Database → transaction pooler |
| `DIRECT_URL`                           | Postgres для міграцій    | там само, session pooler                 |
| `NEXT_PUBLIC_SUPABASE_URL`             | Проєкт Supabase          | Supabase → Project Settings → API keys   |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Публічний ключ           | там само, ключ виду `sb_publishable_…`   |
| `CRON_SECRET`                          | Захист крон-ендпоінта    | `openssl rand -base64 32`                |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY`         | Публічний ключ пушів     | `npx web-push generate-vapid-keys`       |
| `VAPID_PRIVATE_KEY`                    | Приватний ключ звідти ж  | те саме                                  |
| `VAPID_SUBJECT`                        | Контакт для push-сервісу | `mailto:` або `https://`                 |

Публічний ключ VAPID навмисно лежить лише в `NEXT_PUBLIC_`-змінній. Він
потрібен і браузеру, і серверу, а публічний за визначенням — друга, серверна
копія того самого значення давала б хіба що спосіб їм розійтися, а
розходження тут дає не помилку, а мовчазну відмову push-сервісу.

## Розгортання

1. Створити проєкт на [supabase.com](https://supabase.com) і проєкт на Vercel
   з цього репозиторію.
2. Регіон функцій Vercel поставити поруч із базою (для `eu-west-1` це `dub1`).
   Типовий регіон Vercel — США, і кожен запит ходив би через океан.
3. Додати змінні у Vercel → Project Settings → Environment Variables.
4. Накотити міграції: `vercel env pull .env.local` і `npm run db:migrate`.
5. Задеплоїти, відкрити застосунок, увійти.

Крон із `vercel.json` підхоплюється сам — окремо його вмикати не треба.

## Supabase: що налаштувати руками

Один крок у панелі, без якого вхід не працює, — і він мовчазний: помилки не
буде, лист просто прийде не такий.

Authentication → Email Templates → **Magic Link**. Правило: якщо в шаблоні є
`{{ .ConfirmationURL }}`, Supabase шле посилання; якщо `{{ .Token }}` —
шестизначний код. Потрібен код, тож у шаблоні лишається лише він:

```html
<h2>Вхід у «Пальне»</h2>
<p>Код: {{ .Token }}</p>
```

**Пошта.** Вбудований відправник Supabase — кілька листів на годину на весь
проєкт, і в їхній документації позначений як не для продакшену. Коли впреться,
Authentication → Emails → SMTP Settings і власний відправник; коду це не
торкається.

## Айфон: іконка й сповіщення

Пуш на iOS працює **тільки** для застосунку, доданого на головний екран
(iOS 16.4+). Тому порядок такий:

1. Відкрити застосунок у Safari.
2. «Поділитися» → «На Домашній екран».
3. Запустити вже з іконки.
4. `/settings` → увімкнути «Нагадування про пробіг» → дозволити сповіщення.
5. Натиснути «Перевірити» — має прийти сповіщення.

Поки застосунок відкривають як звичайну вкладку, на головній сторінці висить
підказка про це. Після встановлення вона зникає сама.

## Крон

Один щоденний запуск, `0 17 * * *` — це 20:00 за Києвом улітку і 19:00 взимку.
Безкоштовний план Vercel дозволяє запуск не частіше разу на добу, тож «в
останній день місяця» окремим розкладом там не задати: день перевіряється в
коді, а не в `vercel.json`.

Задача одна — **нагадування про пробіг**. Іде в останній день місяця, і лише
якщо показання за цей місяць ще немає: нагадування про вже зроблене привчає
змахувати сповіщення не читаючи.

Перевірити вручну:

```bash
curl -H "Authorization: Bearer $CRON_SECRET" \
  https://<домен>/api/cron/daily
```

У відповідь приходить звіт — він же лягає в логи Vercel:

```json
{
  "date": "2026-08-28",
  "reminder": {
    "status": "skipped",
    "reason": "not-last-day",
    "month": "2026-08"
  },
  "ok": true
}
```

Невдалий запуск віддає 500 — щоб у списку крон-задач його було видно
червоним, а не серед однакових зелених рядків.

## Команди

| Команда                 | Що робить                               |
| ----------------------- | --------------------------------------- |
| `npm run dev`           | Розробка                                |
| `npm run build`         | Продакшн-збірка (вона ж перевіряє типи) |
| `npm run check`         | Формат, лінт, типи, тести — усе разом   |
| `npm test`              | Тести                                   |
| `npm run test:watch`    | Тести у стежному режимі                 |
| `npm run test:coverage` | Покриття по `domain` і `lib`            |
| `npm run db:generate`   | Згенерувати міграцію зі змін у схемі    |
| `npm run db:migrate`    | Накотити міграції                       |
| `npm run db:studio`     | Переглянути базу                        |

`db:push` навмисно не виведено в скрипти: він змінює схему без сліду в
історії, а міграції мають лишатись відтворюваними.

Перед пушем варто прогнати `npm run check`, а після зміни залежностей —
`rm -rf node_modules && npm ci`. Vercel деплоїть саме через `npm ci`, і
розсинхронізований `package-lock.json` ламає збірку там, хоч локально
`npm install` і мовчить.

## Тести

Покривають те, де помилка тиха: обчислення грошей і обʼєму, київські дати,
агрегації статистики, редюсер звʼязаних полів форми, а також рішення, які
видно лише в проді — коли видаляти мертву push-підписку і що робити щодня
в крону.

```bash
npm test
```

Компоненти й запити до бази тестами не покриті свідомо: перші перевірялись
браузером під час розробки, другі — на справжній схемі. Тримати для них
моки означало б підтримувати другу копію застосунку, яка розходиться з
першою мовчки.

## Рішення, які варто знати

**Гроші й обʼєм — `numeric(10,2)`, а не float.** У коді вони живуть як цілі
соті з окремим типом `Decimal2`, тож `0.1 + 0.2` тут не «попливе». Заправка
зберігає всі три числа — літри, ціну і суму, — хоча одне завжди похідне:
інакше кожен перерахунок історичного запису давав би трохи інший результат
через округлення.

**Усі дати київські.** Сервер працює в UTC, і о 22:00 за Києвом там уже
наступна доба. Голого `new Date()` у бізнес-логіці немає — дата завжди
береться через `lib/date`.

**Push-підписка видаляється лише на 404 і 410.** Це остаточне «такої підписки
немає». Після 429, 500 чи обриву мережі збій рахується, але підписка живе:
викидати пристрій через одну помилку означало б мовчки відписати його від
нагадувань.

**Service worker не кешує запитів.** Обробника `fetch` у ньому немає взагалі:
застосунок працює тільки з живими даними, і закешована сторінка з учорашніми
заправками була б гіршою за чесне «немає мережі».

**Код із листа, а не посилання.** На айфоні посилання з пошти відкривається
в Safari, а застосунок із головного екрана — окреме вікно зі своїм сховищем.
Сесія лягла б не туди, і людина лишилась би незалогіненою саме там, звідки
заходить щодня.

**Вхід перевіряється двічі, і це не надмірність.** Проксі відсіює анонімів
дешево, без бази. `requireUser()` перевіряє по-справжньому — документація Next
прямо каже, що matcher проксі не поширюється на server actions. Третій рубіж,
RLS у самій базі, зʼявиться наступним комітом.

**«Не вдалося звʼязатися» і «код не підійшов» — різні повідомлення.**
Недоступний Supabase приходить таким самим обʼєктом помилки, як і відмова
сервера. Якби вони злились в одне, застосунок радив би перенабрати правильний
код, поки проблема взагалі не на боці людини.

## Свідомо поза скоупом

Чекбокс «повний бак» і обʼєм бака, одометр у кожній заправці, email-нагадування,
мультивалютність, кілька авто, офлайн-режим. Архітектура лишає місце під Face
ID — вхід зроблено через інтерфейс `AuthVerifier`, тож поруч із `PinVerifier`
стане `PasskeyVerifier`, а сесійний шар і middleware не зміняться.
